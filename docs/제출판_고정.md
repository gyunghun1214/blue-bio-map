# 제출판 고정 절차 (2026-10-27 제출, 11-04~05 발표)

발표 자료의 숫자와 QR로 여는 사이트가 발표가 끝날 때까지 같도록, 제출 날 main의 한 커밋을 '발표 기준판'으로 정한다. README '발표 기준판과 제출 뒤 동결'의 절차를 날짜순 할 일로 풀어 적었다. 화면 코드는 바꾸지 않는다. `dist/release.json`을 읽어 안내에 보여 주는 기능은 2026-10-19부터 있다.

이 문서를 더한 PR에서는 `release.json`의 `commit` 값을 넣지 않았고 태그도 만들지 않았다. 아래 단계는 팀이 실행한다.

## 1. 제출 전 (10/26까지)

- [ ] 발표에 쓸 PR을 모두 병합한다. 병합할 때마다 공개 주소를 `?fresh=<임의값>`으로 열어 배포를 확인한다.
- [ ] `docs/발표_숫자_출처.md`의 숫자가 발표 v4와 사이트에 모두 같은지 본다.
- [ ] `BlueBio_발표_v3/03_제출_전_확인.md`의 1~3절(PowerPoint 열기, 슬라이드 쇼, 제출 파일)을 마친다.

## 2. 제출 날 (10/27): 기준판 정하기

1. main 마지막 커밋을 확인한다.
   ```
   git fetch origin main && git log -1 --format='%h %s' origin/main
   ```
2. `dist/release.json`의 `commit`에 그 7자리를 넣는 PR을 만든다. 이 파일 하나만 바꾼다. 날짜가 바뀌면 `date`도 고친다.
   ```json
   {"label": "발표 기준판", "date": "2026-10-27", "commit": "abc1234"}
   ```
3. 그 PR을 병합한다. 자동 배포가 끝나면 공개 주소를 `?fresh=<임의값>`으로 열고, 상단 '연구 프로토타입 ▾' 안내에 "발표 기준판 2026-10-27 · 커밋 abc1234"가 보이는지 확인한다.
4. 3에서 병합한 커밋에 태그를 단다. 태그 이름은 README와 같다.
   ```
   git fetch origin main
   git tag final-2026-10-27 <3에서 병합한 커밋>
   git push origin final-2026-10-27
   ```
5. 사전 등록 PR(#255)을 squash로 병합했다면, 사전 등록 커밋에도 태그를 단다. 그래야 그 커밋이 남는다.
   ```
   git tag prereg-mbpi-origin-2026-10 6b06ca8 && git push origin prereg-mbpi-origin-2026-10
   ```

## 3. 제출 뒤 (10/27~11/5)

- 화면 숫자를 바꾸는 병합은 하지 않는다. main 병합은 곧바로 공개 주소에 배포된다.
- 그래도 병합해야 하면, 병합 **전에** 두 가지를 본다.
  - `BlueBio_발표_v3/02_팀이_정할_것.md` 9번에서 팀이 고른 방식. (가)는 숫자가 바뀌는 배포를 멈추고, (나)는 대조한 뒤 배포한다.
  - `BlueBio_발표_v3/03_제출_전_확인.md` 4절 '사이트와 숫자 맞추기'의 숫자가 그대로인지.
  - 하나라도 바뀌면 그 병합은 11/5 발표가 끝난 뒤로 미룬다.
- 오탈자처럼 꼭 고쳐야 할 것은 고친 내용을 먼저 병합한다. 그다음 `dist/release.json`만 바꾸는 PR로 `commit`을 새 main 커밋으로 바꾸고, `"note": "11-02 오탈자 수정"`처럼 무엇을 바꿨는지 적는다. 안내에는 "발표 기준판 2026-10-27 · 커밋 def5678 · 11-02 오탈자 수정"으로 보인다. 태그 `final-2026-10-27`은 옮기지 않는다.

## 4. 발표 뒤 (11/6~)

- 동결을 풀고 밀린 PR을 병합한다.
- `release.json`의 `commit`은 다음 발표나 제출 때까지 그대로 둬도 된다. 비우면 안내가 지표 버전 표시로 돌아간다.
